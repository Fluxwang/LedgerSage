# 记账方向：让收入与转账记得出来，让自动补全改得动

Status: open
Labels: ready-for-agent

术语一律以 [`CONTEXT.md`](../../CONTEXT.md) 为准（分录行、方向、自动补全、追问、待确认写入）；架构决策见 [`docs/adr/`](../../docs/adr/)，本文不重复论证，只引用。本期核心依据是 ADR 0014（资金流向）与 ADR 0015（自动补全可编辑）。

## Problem Statement

用户说「今天发工资了，发了5000」，BeanChat 弹出的追问是「第 1 笔请选择付款账户」，候选里清一色是资产账户。工资不是从某张卡里付出去的，这个问题本身就问错了 —— 用户没有任何选项可以选对。

就算用户随手选了一张银行卡，写进账本的也是符号颠倒的一笔：银行卡记负数、工资账户记正数，等于把「收到 5000」记成了「花掉 5000」。而错误不会被拦下 —— 待确认写入的确认卡只有「确认」和「拒绝」两个动作，用户发现账户不对时唯一的补救是整条拒绝、把话重说一遍。

用户还会误以为是自己的账本缺了收入账户。实际上账本里有 19 个 Income 账户，只是它们（连同其余 100 多个账户）都没有把中文名写在 `open` 指令的 `name:` meta 上，于是追问候选全是英文账户名，喂给 LLM 的语义信号（ADR 0009）也是空的。

同一条路径上还堵着两类交易：转账（历史上 47 笔，比纯收入的 44 笔还多）在追问里选不到对手方；三条及以上分录行的交易（历史上 47 笔）会被静默压成两条，差额凭空消失。

最后，每一次正常追问都要多烧一轮 LLM：抽取发现「缺账户」时会打回重新分类，而重新分类的结果必然还是记账。实测一条工资消息因此多花 8.3 秒。

## Solution

把「一笔交易的两条分录行代表什么」这件事定死为**资金流向**：一条是资金流出方（记负数），一条是资金流入方。**方向**（支出 / 收入 / 转账）不再是谁填的字段，而是由两条分录行的账户前缀推导出来的结果 —— 收入账户永远在流出侧，支出账户永远在流入侧，两端都是资金或负债账户就是转账。这条不变量在交易值对象**构造时**执行，方向反了的交易根本构造不出来。

于是三种方向共用同一条对话路径：用户说「发工资5000」，系统认得出这是收入，追问问的是「钱进了哪张卡」而不是「从哪张卡付的」，写出来的账本文本符号正确。

追问本身也修好：候选按「这个商户你以前最常用的」排序、不够的用「你全局最常用的」补齐，数量上限从 8 提到 12（可配置）。分类账户的候选命中率因此从 8% 升到 87%。

自动补全从只补一条分录行扩展到两条都补，让高置信场景（历史上 53 次充值全是同一张卡同一个分类）一次都不用点。作为前提，待确认写入变成**可编辑的**：确认前能直接改掉猜错的账户，改完重新校验、重新渲染预览。这不是优化项 —— 实测把置信度阈值拉到极限，准确率也只有 87%，剩下的错误不可能靠调参消除（ADR 0015）。

模型表达不了的两类形态被**显式拒绝**而不是静默凑合：多条分录行的交易直接告诉用户请在账本里手写；Equity 账户排除在对话记账之外。

## User Stories

1. 作为记账用户，我想说「今天发工资了，发了5000」就被识别为收入，这样我不用换一种说法去迁就系统。
2. 作为记账用户，我想在收入场景下被问「这笔钱进了哪个账户」而不是「付款账户」，这样问题本身是可回答的。
3. 作为记账用户，我想在收入的追问里看到我的资产账户作为候选，这样我能选到正确答案。
4. 作为记账用户，我想让工资记出来的账本文本是「收入账户记负数、银行卡记正数」，这样它与我手写的历史记录形态一致。
5. 作为记账用户，我想在说「支付宝转300到微信」时被识别为转账，这样我不必为了记一笔转账去手写账本。
6. 作为记账用户，我想在转账的追问里看到另一个资金账户作为候选，这样我能选到转入方。
7. 作为记账用户，我想在说「还信用卡2000」时被正确记成资金账户到负债账户的转账，这样我的信用卡余额是准的。
8. 作为记账用户，我想让系统在我把两个账户说反时自动纠正，而不是报错打断我，这样我不用关心会计方向。
9. 作为记账用户，我想让支出记账在这次改动后行为不变，这样我最常用的路径不会被改坏。
10. 作为记账用户，我想在追问候选里先看到我常用的账户，这样我通常点第一个就对了。
11. 作为记账用户，我想在面对 67 个支出分类时仍能在候选里找到对的那个，这样我不必每次都手打账户名。
12. 作为新商户的记账用户，我想在没有历史时也能看到一批合理的候选（我全局最常用的），这样冷启动不至于一个候选都没有。
13. 作为记账用户，我想让候选按钮的数量可以按部署调整，这样在手机上不会滑很久。
14. 作为记账用户，我想在追问里直接打字输入账户名，这样候选里没有时我仍有出路。
15. 作为记账用户，我想在我打的字匹配到多个账户时被再问一次，而不是被系统默默挑一个，这样我不会因为打了「银行」就被安到 Bank-01 上。
16. 作为记账用户，我想让追问的问题文案直接说明缺什么，而不是把内部诊断信息重复一遍，这样我一眼看得懂要我干什么。
17. 作为记账用户，我想让一次普通的追问不要多花近十秒，这样对话是跟得上的。
18. 作为记账用户，我想让系统在我没提账户时用历史替我填上，这样常规消费我一句话就能记完。
19. 作为记账用户，我想让我明确说出的账户永远优先于系统的猜测，这样我说了「微信」就一定是微信。
20. 作为记账用户，我想让付款账户也能被自动补上（而不是每次都问），这样充深圳通这种固定组合我一次都不用点。
21. 作为记账用户，我想在确认卡上看出哪些账户是系统猜的，这样我知道该重点核对哪一行。
22. 作为记账用户，我想在确认前直接改掉猜错的账户，这样我不必整条拒绝重说一遍。
23. 作为记账用户，我想让改完账户后的预览立刻更新成改后的样子，这样我确认的就是我看到的。
24. 作为记账用户，我想让我改成一个不存在的账户时被拦下并告知，这样我不会写出一本加载不了的账本。
25. 作为记账用户，我想让确认后落盘的内容是我改过的版本，这样编辑是真的生效而不是摆设。
26. 作为记账用户，我想在追问和确认卡上看到中文账户名而不是英文路径，这样我不用在脑子里翻译。
27. 作为记账用户，我想让系统用中文显示名去理解我说的话，这样我说「饭卡」它能找到校园一卡通。
28. 作为记账用户，我想让那些原本没写中文名的账户（主要是收入账户）也补上名字，这样收入场景的候选质量和支出一样好。
29. 作为记账用户，我想在说出一笔需要三条分录行的交易（如工资扣五险一金）时被明确告知系统记不了、请手写，这样我不会以为记上了而其实差额消失了。
30. 作为记账用户，我想让期初余额、对账差额这类权益账户不出现在对话记账的候选里，这样候选列表里没有我用不上的东西。
31. 作为记账用户，我想让这些权益账户在账本查询与统计里照常可见，这样排除只发生在记账入口。
32. 作为运维者，我想用环境变量调置信度阈值和候选数量上限，这样不同部署可以有不同的松紧。
33. 作为开发者，我想让方向不变量由交易值对象自己保证，这样绕过 Agent 的写入路径（HTTP、将来的导入脚本）也不会写出反向的账。
34. 作为开发者，我想让抽取质量疑点和字段缺失是两个独立的东西，这样打回重新分类只发生在它真该发生的时候。
35. 作为开发者，我想让频次分布按分录行角色切分，这样三种方向共用一套逻辑、转账不需要特例。

## Implementation Decisions

**账本网关 —— 方向不变量落在交易值对象上（ADR 0014）**

交易输入值对象新增构造期校验：收入账户落在流入侧时自动交换两条分录行（支出账户落在流出侧**不**换位——那是退款的真实形态，换位会把退款写成支出，见 ADR 0014）；同时暴露一个派生的「方向」属性（支出 / 收入 / 转账），由前缀推导，不作为可赋值字段存在。渲染逻辑不动 —— 归一化之后，现有「流出侧挂负数」的符号规则本来就是正确的。

归一化是静默换位，不报错。LLM 把两个账户选反属于常见且可自动纠正的错误，没有理由为此打断用户。

**账本网关 —— 交易历史改为三元组**

历史采集从「只取支出那条分录行」改为返回 `(商户, 流出账户, 流入账户)`，覆盖三种方向，并在采集时排除权益账户。这是两个频次分布的数据来源。

**置信度 —— 两个分布，按分录行角色切分（ADR 0004 的口径不变）**

维护 `商户 → 流出账户` 与 `商户 → 流入账户` 两个频次分布，各自计算最高频占比、各自判阈值、各自决定是否自动补。归一化保证了角色位置稳定，因此同一套逻辑在三种方向下都成立。ADR 0004 对置信度的定义（最高频账户的占比）不需要改 —— 它本来就是按单个账户定义的。

**Agent 图 —— `issue` 与 `missing` 拆成两个字段（ADR 0001 修订）**

`issue` 只装抽取质量疑点（含疑问词、日期是范围、缺明确金额主体、商户是品类词、需要多条分录行），负责打回重新分类；新的 `missing` 装结构化的缺失信息（第几笔、缺哪一侧分录行），直接进追问。路由改为三路：有 `issue` 且没打回过 → 打回；有 `missing` → 追问；都没有 → 产出待确认写入。

**Agent 图 —— 追问的候选集由已知的那条分录行推导**

已知流入侧是支出账户 → 候选给资金与负债账户；已知流出侧是收入账户 → 候选给资金账户；已知一侧是资金账户而另一侧未知 → 候选给支出、收入与其余资金账户（即三种方向都还开着）。排序为「该商户的频次分布优先，不足的用全局频次补齐」，数量上限读配置。权益账户不进任何候选集。

追问文案由 `missing` 生成，不再拼接诊断字符串。

**Agent 图 —— 自由文本匹配到多个账户时再追问一次**

追问接受自由文本并做子串匹配。匹配到多个账户时不再取第一个，而是把这些账户作为候选再问一次。

**抽取模型 —— prompt 重写**

现有 prompt 写的是「from_account 是付款账户，to_account 是支出或收入账户」，这句话本身是收入记反的源头之一。改为资金流出方 / 流入方，并列明三种方向各自的形态。向量召回的相似历史是带真实符号的账本原文，与新语义一一对应，prompt 中可直接指示照其符号填写。

**抽取 —— 多条分录行的交易显式拒绝**

在确定性规则里增加一条：一条消息里出现多个金额且语义上属于同一笔（出现「扣」「其中」「到手」「实发」这类词）时，判定为需要多条分录行，作为抽取质量疑点处理，回复说明当前只支持两条分录行、请在账本里手写。

**待确认写入 —— 可编辑（ADR 0015）**

新增一个修改待确认写入的接口，允许在确认前替换其中某笔交易的账户。每次修改都重新跑校验并重新渲染预览，理由与 ADR 0012 中「确认时重新校验」一致：预览不能变成过期的通行证。修改不改变待确认写入的过期时间与确认路径。

**配置 —— 两个旋钮走环境变量（ADR 0011）**

置信度阈值默认值从 0.70 改为 0.80；新增追问候选数量上限，默认 12。两者都通过既有的 pydantic-settings 读取环境变量与 `.env`。不使用 `config.yaml` —— 它已被 ADR 0011 废弃，代码里没有任何地方读它。

**前端 —— 确认卡上的账户可点击修改**

确认卡为每笔交易的两条分录行提供账户选择入口，选择列表与追问候选同源（频次排序 + 显示名）。自动补上的账户需要与用户明确给出的账户在视觉上可区分。

**账本数据 —— 显示名迁移（ADR 0009）**

对现存账本执行一次显示名迁移，把 `open` 指令行尾的中文注释搬到 `name:` meta（106 个账户中 94 个可自动迁移）。剩余 12 个没有注释的账户（其中 10 个是收入账户）需要人工拟定中文名后写入。这是对已有行的改写，属于 ADR 0002 追加式写入之外的例外，与 ADR 0013 的删除并列；迁移在账本仓库中单独提交，执行前需要用户确认。

**经验数据（决定阈值与候选数量的依据）**

在 1161 笔两条分录行的历史交易上做留一验证：

| 阈值 | 流出侧 自动补率 / 准确率 | 流入侧 自动补率 / 准确率 |
|---|---|---|
| 0.70 | 41% / 84% | 32% / 80% |
| 0.80 | 37% / 85% | 29% / 85% |
| 0.90 | 33% / 87% | 28% / 86% |
| 1.00 | 29% / 87% | 26% / 85% |

候选命中率（同一数据集）：

| 排序方式 | 流出侧 前 8 | 流入侧 前 8 | 流入侧 前 12 |
|---|---|---|---|
| 字母序（现状） | 96% | 8% | 11% |
| 商户频次 | 60% | 57% | 57% |
| 商户频次 + 全局补齐 | 99% | 82% | 87% |

## Testing Decisions

好的测试只断言外部可观察的行为：用户看到的事件、追问里出现的候选、最终落进账本的文本。不断言节点内部的中间字段、不断言函数被调用了几次、不断言私有属性。

**主接缝：对话运行的事件流。** 用一个固定响应的假模型替换 LLM 边界（该边界已经是 Protocol，现有图测试就是这么搭的），配一份临时账本与临时 SQLite，断言运行吐出的事件序列。这是后端唯一能观察到「用户实际看到什么」的入口。在这条接缝上覆盖：

- 收入端到端：假模型吐出收入场景的抽取结果，断言追问问的是资金流入而非付款账户、候选里是资产账户、确认后落盘的账本文本中收入账户在负数侧。
- 转账端到端：两端都是资金账户，断言候选里出现另一个资金账户，落盘文本正确。
- 归一化：让假模型故意把两个账户吐反，断言最终渲染的符号仍然正确。
- 打回路由：缺账户的场景下，断言事件序列里只出现一次分类，不再有多余的那一轮。
- 候选集：断言排序（商户常用的在前）、数量上限受配置控制、权益账户不出现。
- 自动补全：构造高置信历史，断言两条分录行都被补上、不再触发追问；构造用户明确说了账户的场景，断言猜测不覆盖它。
- 多条分录行：断言被拒绝且回复说明，没有产出待确认写入。

**第二接缝：待确认写入服务。** 沿用现有的两段式写入测试搭法：修改待确认写入里的账户 → 预览重新渲染 → 确认后落盘的是改后的值；改成不存在的账户 → 报错且预览不变；修改不影响过期判定。不走 HTTP 层，因为对应路由是薄壳，现有的同类测试也都在服务层。

**补充（沿用已有测试文件，不新增接缝）：** 频次排序与全局补齐的组合逻辑放在现有的置信度测试里直接测纯函数；交易值对象的归一化放在现有的账本测试里。显示名迁移已有测试文件，只需补上「无行尾注释的账户不被误迁」这一例。

**前端不做自动化测试。** `web/` 目前没有任何测试基建，确认卡可编辑的交互靠手动验证。

**先红后绿。** 收入端到端那一条应当在改动前就能写出来并且是失败的 —— 它正是本 spec 要修的 bug。

## Out of Scope

- **多条分录行的交易**。本期只做显式拒绝，不做支持。补齐它需要把交易值对象从两个账户字段改成分录行列表，连带改渲染、追问与确认卡，是一次结构性手术。
- **把收入账户当往来账户反向使用**（历史上 5 笔）。归一化会把它换位成标准收入方向，这种写法从此对话记不出来，手写不受影响。
- **权益账户的对话记账**。期初余额与对账差额不是「我今天花了多少」这类场景。
- **修改已落盘的交易（amend）**。与本期无关，仓库仍只有追加与删除两种写入（ADR 0002 / 0013）。
- **per-user 偏好体系**。阈值与候选数量本期走环境变量；ADR 0011 提到的 `user_settings` 表不在本期建。
- **转账独立成新意图**。已在 ADR 0014 中否决。
- **前端测试基建**。
- **向量索引重建**。索引存的是账本原文，与本次字段语义变更无关，不需要重跑。
- **多币种**。历史账本中存在 USD / HKD / 加密货币账户，本期不处理跨币种交易。

## Further Notes

用户最初的判断是「我的账本里没写收入账户」。实际不是 —— 收入账户有 19 个，缺的是它们的中文显示名，以及系统这一侧对收入方向的支持。spec 的实现顺序上，显示名迁移可以先做且独立可验证，它会立刻改善追问候选的可读性。

`Income` 与 `Expenses` 同时出现在两侧的交易（历史上有零星几笔）不需要特殊处理：收入账户与支出账户同时落反时只按收入这一个条件换位一次，结果恰好是正确形态。

本期还顺带修一个与主线无关的独立缺陷：周期换算函数引用了一个已被删除的 import，走到该分支会抛 `NameError`。建议单独提一张票，不要混进本 spec 的改动。

历史账本在本次讨论期间被用户合并过一批资产账户（若干余额账户并入主账户，并改写了一千余笔历史交易的引用）。上述所有统计数字均基于合并后的账本重算，合并前后结论一致。
