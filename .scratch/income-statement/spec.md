# 收支表：账户层级 × 连续多个月的矩阵

Status: open
Labels: ready-for-agent

术语一律以 [`CONTEXT.md`](../../CONTEXT.md) 为准（发生额、汇总账户、末级账户、储蓄率）；本期唯一新增的架构决策是 [ADR 0016](../../docs/adr/0016-parent-accounts-are-not-postable.md)（汇总账户不能直接记账），本文只引用、不重复论证。

## Problem Statement

统计页的「收支表」标签目前用 `/dashboard` 顶着：它只能给出**单个区间**的支出分类合计和近六月的月度支出总额，页面底部挂着一张「待 `GET /statements/income`」的占位卡。设计稿要的是另一种东西——行是账户层级（支出 → 饮食 → 餐饮），列是连续的多个月，每一行带一条趋势迷你条，点格子能下钻到对应的流水。

拼不出来的原因有三个：

1. **没有「账户 × 月」的聚合**。后端只有「按账户」或「按月」的单维汇总，前端要自己发 N 次请求再拼，而且拿不到汇总账户的合计。
2. **收入侧完全没有出口**。`/dashboard` 的分类合计只算 `Expenses:`，整个 REST 面上没有任何接口返回 `Income:` 的聚合，所以储蓄率一直显示「—」。
3. **汇总账户没有显示名**。账本里只有末级账户写了 `open`（如 `Expenses:Food:Dining` 餐饮），中间层 `Expenses:Food` 从未开户，表格里只能显示英文段名。而一旦给它开户，它又会混进对话记账的候选——模型可能把「买了点吃的」直接记到 `Expenses:Food` 上，收支表里就多出一块不属于任何子类、下钻也找不到的钱。

## Solution

新增一个只读接口 `GET /statements/income`，一次返回请求范围内**每个收支账户在每个月的发生额**，汇总账户的合计由后端算好。接口只给矩阵本身，所有派生数字（总支出、总收入、结余、储蓄率、峰值月、每月构成、趋势迷你条）都由前端从这一份矩阵里推导，数据只有一个来源，合计不可能和明细对不上。

同时落实 ADR 0016：有子账户的账户只用来挂预算、出报表和做筛选前缀，对话记账不再提供它。这样用户就可以放心给 `Expenses:Food`、`Expenses:Housing` 这些中间层补上 `open` 和中文名。

## User Stories

1. 作为记账用户，我想在一张表里看到最近几个月每个支出分类各花了多少，这样我能看出哪个分类在涨。
2. 作为记账用户，我想看到「饮食」这样的上层分类合计，而不只是一堆末级分类，这样我先看大头再往下看细节。
3. 作为记账用户，我想让上层分类显示我起的中文名，这样表格读起来不像在看代码。
4. 作为记账用户，我想在同一张表里看到收入，这样我知道每个月是攒下了还是花超了。
5. 作为记账用户，我想看到这段时间的储蓄率，这样我有一个衡量自己的单一数字。
6. 作为记账用户，我想让退款冲减当月的支出，这样买了又退的东西不会让我看起来花了更多钱。
7. 作为记账用户，我想让收支表的数字和仪表盘、对话里「这个月花了多少」的回答一致，这样我不会怀疑哪个是错的。
8. 作为记账用户，我想知道当前月份还没过完，这样我不会误以为这个月花得少。
9. 作为记账用户，我想选择看几个月的范围，这样我既能看近况也能看半年、一年的趋势。
10. 作为记账用户，我想点某个分类某个月的格子就看到那几笔流水，这样我能找到钱具体花在了哪。
11. 作为记账用户，我想让每一行带一条小趋势条，这样不用逐个读数字就能看出走势。
12. 作为记账用户，我想让整段时间都是零的分类不出现在表里，这样表格不会被空行撑满。
13. 作为记账用户，我想在有外币交易没被计入时得到提示，这样我知道这张表不是全部。
14. 作为记账用户，我想在说「买了点吃的」时被记到餐饮或买菜这样的具体分类上，而不是笼统的「饮食」，这样我的报表每一块钱都能下钻到具体分类。

## Implementation Decisions

**接口形状**

```
GET /statements/income?start=2026-05&end=2026-10
```

- `start` / `end` 只接受 `YYYY-MM`，后端换算为「`start` 月 1 日」到「`end` 月最后一天」，`end` 落在当月时截到今天。
- 都不传时默认最近 6 个月（含当月）；跨度超过 24 个月、`start` 晚于 `end`、`end` 在未来月份时返回 422。
- 不接受 `account` 与 `tag` 参数：前端要从同一份矩阵里同时推出收入和支出，按账户过滤会让储蓄率算不出来；账本目前没有标签概念。

```jsonc
{
  "currency": "CNY",
  "skipped_currencies": [],
  "periods": [
    { "period": "2026-05", "partial": false },
    { "period": "2026-10", "partial": true, "through": "2026-10-27" }
  ],
  "rows": [
    { "account": "Expenses", "display_name": "支出", "depth": 0, "cells": ["3201.50", "…"] },
    { "account": "Expenses:Food", "display_name": "饮食", "depth": 1, "cells": ["…"] },
    { "account": "Expenses:Food:Dining", "display_name": "餐饮", "depth": 2, "cells": ["…"] }
  ]
}
```

- `cells` 与 `periods` 按下标一一对应、长度相等；某月没有发生额填 `"0.00"`，不省略。金额一律两位小数的字符串。
- `partial` 只会出现在最后一列，且仅当它是当前月份时为 true，`through` 给出截止日。

**金额口径——发生额**

格子金额是该账户（含全部子孙账户）在该月的**发生额**：同一账户上的流入流出相抵，退款冲减支出。这与仪表盘分类合计、对话查询用的是同一口径，账本网关里已有的按分录行折叠逻辑就是这个算法，直接复用，不另写一套。对外一律取正数：收入账户在账本里是负数，返回前取反。

**行的组织**

- 只出 `Income` 与 `Expenses` 两棵树，资产、负债、权益不在收支表的范围内。
- 账户树由**账本里实际出现过分录行的账户 + 已开户的账户**共同推出：一个账户的每一级前缀都是树上的一个节点，即使那一级从未开户（例如用户还没给 `Expenses:Food` 补 `open`）。
- 汇总账户的金额 = 自身分录行 + 全部子孙账户（ADR 0016：旧交易可能直接记在汇总账户上，不能从报表里消失）。
- 显示名优先取该账户 `open` 上的 `name:`；没开户或没写 `name:` 时退回账户名的最后一段；两个根固定为「收入」「支出」。
- 整个范围内每个月都是零的行不返回（汇总账户只要有一个子孙非零就保留）。
- 行按深度优先排列；同一父节点下的兄弟按整段范围的合计从大到小排，合计相同按账户名排。根的顺序固定为先 `Income` 后 `Expenses`。

**币种**

只统计账本声明的主币种（`operating_currency`）。范围内出现过、但因币种不同被跳过的分录行，其币种去重后列进 `skipped_currencies`，前端据此标注「有外币交易未计入」。不做汇率折算。

**接口落点**

账本网关新增一个按「账户 × 月」聚合的方法，返回上面的结构；API 层在现有账本路由里加一个薄壳，只负责参数解析与校验。它不经过 Agent——报表是确定性聚合，不该花 LLM 的钱（与 ADR 0006 对仪表盘的处理一致）。

**汇总账户不能直接记账（ADR 0016）**

「是不是汇总账户」由账户树推出：存在任何以 `该账户:` 开头的已开户账户，它就是汇总账户。三处收口：

- 记账抽取时喂给模型的账户表里去掉汇总账户，模型从一开始就看不到它。
- 追问候选与确认卡编辑器的候选（同一个「允许的账户」函数）排除汇总账户。
- 账本写入前的校验拒绝汇总账户，报错信息说明「这是汇总账户，请选择它下面的具体分类」。确认时会重新校验（ADR 0012），所以即使某条待确认写入是在补开子账户之前生成的，也落不了盘。

预算设置**不受影响**，汇总账户本来就是挂预算的主要对象。

**前端**

- `api.ts` 的 `IncomeStatement` 类型按上面的响应改写，删掉 `totals` 与 `composition`。
- 前端从 `rows` 推导：总支出、总收入取两个根行各月之和；结余 = 收入 − 支出；储蓄率按 `CONTEXT.md` 定义，收入为零显示「—」；峰值月取 `Expenses` 根行最大的那一列；每月构成取 `Expenses` 下第一层子行；迷你趋势条直接画该行的 `cells`。
- `partial` 的列头标注「截至 MM-DD」。
- 下钻：点格子切到「流水」标签，带上该账户前缀与该月的起止日期，复用现有的 `GET /transactions`。流水页目前的时间范围来自页面顶部的单区间切换，需要能接受一个外部传入的自定义范围。
- 统计页顶部的「本月 / 本周 / 本年」切换不驱动收支表，收支表有自己的月份范围选择。

**账本数据（用户手动，不属于代码改动）**

用户给 `Expenses:Food`、`Expenses:Housing` 等中间层补 `open` 与 `name:`。代码改动落地之后再做，否则补开的汇总账户会先混进记账候选。

## Testing Decisions

好的测试只断言外部可观察的行为：接口返回的结构与数字、对话里出现的候选、能否落盘。不断言内部中间结构和调用次数。

**主接缝：账本网关的「账户 × 月」聚合。** 用临时账本写入构造好的交易后直接调用网关方法（沿用现有账本测试的搭法），覆盖：

- 汇总账户等于子孙之和，且包含直接记在汇总账户上的旧交易。
- 退款冲减当月支出；收入取正数。
- 没开户的中间层照样出现在树上，显示名退回最后一段；开了户的用 `name:`。
- 全零行被剔除；兄弟按合计降序。
- 外币分录行不计入，币种出现在 `skipped_currencies`。
- 与仪表盘分类合计在同一区间上数字一致——这是「三处对得上」的回归保护。

**第二接缝：HTTP 参数校验。** 默认范围、`YYYY-MM` 格式、跨度上限、未来月份、当前月 `partial` 标记。走 API 层，因为这些规则就长在路由的参数解析上。

**第三接缝：对话运行的事件流（汇总账户不可记账）。** 沿用现有图测试的假模型搭法：账本里同时开了 `Expenses:Food` 与 `Expenses:Food:Dining`，断言追问候选里没有 `Expenses:Food`；假模型硬吐出 `Expenses:Food` 时，断言写入被拒绝且回复说明原因；确认时重新校验同样拒绝。

**前端不做自动化测试。** `web/` 没有测试基建，矩阵渲染与下钻靠手动验证。

**先红后绿。** 「汇总账户等于子孙之和、含旧交易」与「候选里没有汇总账户」两条应在改动前写出来并且是失败的。

## Out of Scope

- **资产负债表 `GET /statements/balance`**。另一张报表，另开规格。
- **按周、按年的列粒度**。只按月。
- **汇率折算**。只统计主币种。
- **标签筛选**。账本目前不用标签。
- **迁移已记在汇总账户上的旧交易**。它们照样合法、照样计入报表，不做拆分。
- **账户树左栏改用新接口**。`GET /accounts/tree` 是另一个待实现接口，本期不动。
- **导出 CSV**。

## Further Notes

建议的实现顺序：先落「汇总账户不可记账」（小、独立可验证，而且是用户补 `open` 的前提），再做网关聚合与接口，最后改前端。三步各自可以单独合并。
