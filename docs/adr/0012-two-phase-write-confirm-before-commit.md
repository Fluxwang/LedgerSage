# 写入分两段：Agent 只产出 diff，落盘由用户点确认

原先 `tools` 节点直接调 `ledger.insert()`，写文件、`git commit` 一气呵成，SSE 把 `receipt` 发出去时木已成舟——用户看到的是既成事实，唯一的补救是事后 `undo`。现在 `tools` 与 `budget` 节点只**渲染**将要写入的文本、算出落点与校验结果，存成一条 `pending_writes` 记录，把 `pending_id` 随 `receipt` 发给前端；真正的 `insert()` / `set_budget()` 发生在用户点「确认写入账本」触发的 `POST /chat/pending/{id}/confirm` 上。

理由是这个产品的信任模型：账本文本是唯一真源，而写进去的内容由 LLM 抽取。抽错账户、抽错金额、把一句话拆成两笔——这些都不是小概率事件，而「先写后撤」与「先看后写」对用户是两种完全不同的东西。前者要求用户在事后比对账本原文才能发现问题，后者把判断放在写入之前，正好是人最愿意花那三秒的时刻。

## Considered Options

**继续先写后撤，靠 `undo` 兜底** 被否决。`undo` 走的是 `git revert`，历史里会留下「写入 + 撤销」两条提交，账本的提交历史变成了 LLM 的试错记录。更要命的是撤销只能整批撤——用户想改的往往是四个字段里的一个（账户选错了），却只能把整笔推倒重来。

**把确认做成对话里的一轮追问（复用 ADR 0007 的 interrupt）** 被否决。追问是「Agent 缺信息、停下来问」，确认是「Agent 信息齐了、等你放行」，两者的失败模式不一样：追问没答复就该超时作废，待确认写入没点确认却应该留着，让用户过一会儿回来还能确认。塞进同一个 interrupt 机制会逼着两种语义共用一套超时与恢复策略。而且 interrupt 挂在 LangGraph 的 checkpoint 上，确认动作就必须是一条用户消息，没法做成一个按钮。

## Consequences

- **`receipt` 事件的含义变了**：它现在描述的是「将要写入什么」，不再是「已经写入了什么」。带 `pending_id` 的是预览，带 `commit` 的是已落盘。前端 `WriteCard` 按这个字段切换两种形态。
- **`reply` 的措辞必须跟着改**，不能再说「已记录 N 笔交易」。
- 向量索引的写入从 `tools` 节点挪到了确认路径——没落盘的交易不该进检索库，否则下一次抽取会拿一笔用户根本没批准的交易当参考。
- `pending_writes` 是**非账务数据**，按项目分工归 `storage`（SQLite），不进账本。确认之后这条记录只作为审计痕迹留着，`commit_sha` 指回账本里的真身。
- **待确认写入会过期**。超过 24 小时的 pending 一律拒绝确认，因为账本可能已经变了（账户被删、月份滚动导致目标文件不同），照着旧预览落盘会写出与预览不符的东西。过期判断在确认时做，不需要后台清理任务。
- 确认时会**重新跑一遍 `_validate`**，而不是信任预览时的结论。预览与确认之间账本可能被改，这一步是防止预览变成一张过期的通行证。
- 与 ADR 0002 不冲突：pending 期间一个字节都不写文件，确认时仍然是一次纯 append。
- 代价是多了一次往返，以及「用户一直不确认」这个新的中间状态。对于记账这种低频、单用户的操作，这个代价是划算的。
