# 删除交易会重写账本文件，写入不再是纯追加

ADR 0002 把写入收敛成了纯 append。流水页需要「删除这笔账目」——把整段交易从账本原文里移除——这件事无论如何都要重写文件中段。本 ADR 明确开这个口子，并划出它的边界。

删除的实现是：按交易 id 定位到源文件与行区间，读入整个文件、去掉那几行、写回、`git commit`。id 不是数据库主键，而是 `base64url("<相对路径>:<行号>:<摘要>")`——前两段来自 Beancount 解析出的 `meta`，第三段是该分录规范渲染文本的 SHA-256 前八位。

## Considered Options

**追加一条冲正分录，账本只增不减** 是最符合复式记账传统的做法，ADR 0002 一个字都不用改。被否决的原因是它解决的不是用户要解决的问题：用户说「删除」，多半是因为这笔**根本就不该存在**（导入重复了、Agent 抽错了、测试时记着玩的），而不是因为发生了一笔冲抵的真实经济活动。给一笔从未发生的支出配一笔从未发生的退款，账本上会留下两笔假账，此后所有按收款方、按分类的统计都会被这对幽灵污染。冲正是会计意义上的更正，不是数据意义上的删除。

**用数据库记一张「已删除」名单，查询时过滤掉** 被否决。这会让账本文件不再是唯一真源——同一份 `.bean` 用 `bean-query` 和用本产品读会得到两个答案，这正是本项目从第一天就拒绝的形态。

## Consequences

- **ADR 0002 的「纯追加」降级为「记账与预算写入是纯追加」**。删除是唯一的例外，它走读—改—写。
- **并发安全的依据没变**：删除同样在每本账本那把 `asyncio.Lock` 里串行，服务仍然必须单 worker。ADR 0002 里那条约束不但没放松，反而更要紧了——纯追加时两个并发写最多是顺序乱了，读改写下就是整段丢失。
- **交易 id 只在某个账本版本内有效**。删掉一笔，它后面所有交易的行号都会变，id 也就跟着变。id 里的摘要就是为此而存在：确认删除时会重新解析、比对摘要，对不上直接返回 409「账本已经变了，请刷新」，而不是闷头删掉旁边那笔。前端每次增删之后都要重新拉列表。
- **只能删本产品认识的东西**：id 解码出的路径必须落在该用户账本根目录内（挡路径穿越），且该行必须确实是一笔 Transaction。
- **撤销复用既有的 `git revert` 通道**。删除提交的 subject 是 `LedgerSage: delete`（改名前为 `BeanChat: delete`，仍可撤销），`Ledger.undo` 的白名单里加了这一条，所以 `POST /transactions/{commit}/undo` 不需要改就能撤销删除。
- 写回时会把连续空行折叠成一个、并规范化文件末尾的换行。代价是删除会顺带调整同文件里人工编辑留下的空行风格，这是接受的。
- `bean-format` 仍然不是运行时依赖：写回的是原始行的子集，不重新格式化任何一行。
