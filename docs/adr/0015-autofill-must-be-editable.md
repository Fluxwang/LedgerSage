# 自动补全的结果必须可编辑，因为调阈值救不了它

Extract 会用历史频次替用户补上没说出口的账户（ADR 0004），补完的结果进入待确认写入，由用户点确认才落盘（ADR 0012）。但确认卡此前只有 `confirm` 与 `reject` 两个动作——猜错了，用户只能整条拒绝、把话重说一遍。直觉上的补救是把 `confidence_threshold` 调高、让系统少猜一点，我们拿真实账本验证了这个直觉，它不成立。

在 1161 笔两条分录行的历史交易上做留一验证（每笔都用「除它之外的同商户历史」去预测，再比对实际账户）：

| 阈值 | `from` 自动补率 / 准确率 | `to` 自动补率 / 准确率 |
|---|---|---|
| 0.70 | 41% / 84% | 32% / 80% |
| 0.80 | 37% / 85% | 29% / 85% |
| 0.90 | 33% / 87% | 28% / 86% |
| 1.00 | 29% / 87% | 26% / 85% |

把阈值一路拉到 1.00——即历史上只出现过唯一一个账户才敢补——准确率也只有 87%。剩下约 13% 的错误与阈值无关，它来自「这次就是和以前不一样」：同一家食堂这顿刷了另一张卡，同一家便利店这次买的是零食而不是饮料。历史再一致也预测不到。

因此：**自动补全可编辑不是优化项，而是自动补全得以存在的前提**。新增 `PATCH /chat/pending/{id}`，允许在确认前改掉待确认写入里的账户，改完重新跑校验、重新渲染预览。阈值同时从 0.70 定为 0.80——那是曲线的拐点（`to` 的准确率 80% → 85%，自动补率只从 32% 掉到 29%），再往上只掉覆盖不涨准确。

## Consequences

- ADR 0012 说的「渲染好但还没落盘的那段账本文本」从此是**可变的**。这与该 ADR 的前提一致：没落盘的东西本来就该可改，当时没做只是因为还没有自动补全把错误值塞进预览。
- 确认前的每一次修改都要重新 `_validate` 并重新渲染，理由和 ADR 0012 里「确认时重新校验」一样：预览不能变成一张过期的通行证。
- **暴露面会随 ADR 0014 扩大**。此前自动补全只作用于 `to_account`，`from_account` 每次都要追问；改为两个分布各自补之后，付款账户也会被自动填。收益是高置信场景（如充深圳通，历史 53/53 全是同一张卡同一个分类）一次都不用点，代价是猜错的机会翻倍——这正是可编辑确认卡必须先于它落地的原因。
- 上表的口径是 payee 精确匹配，而线上的 `account_confidence` 用子串匹配，实际覆盖率会更高、准确率略低。趋势不变，13% 这个量级是下限而非上限。
- 拒绝了「不自动补、只把最高频账户排在追问候选第一位」的方案：它确实永远不会背着用户写错，但也把自动补全的价值全部丢掉——53 次深圳通充值要点 106 次。
