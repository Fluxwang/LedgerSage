# 交易的两条分录行表达资金流向，方向由账户前缀推导

`TransactionInput` 只有 `from_account` / `to_account` 两个字段，而 `render_transaction` 把 `-amount` 写死挂在 `from_account` 上。这套字段名此前没有被赋予明确语义：Extract 的 prompt 说「from_account 是付款账户，to_account 是支出或收入账户」，`prepare_ask` 则把 `from_account` 的候选过滤成 `Assets:` / `Liabilities:`。两处对同一个字段的理解不一致，后果是收入记不出来——追问只给得出资金账户，而即使用户选中了银行卡，渲染出的也是「银行卡 -8000 / 工资 +8000」，符号整个反了。

现在把两条分录行的语义定死为**资金流向**：`from_account` 是资金流出方（记负数），`to_account` 是资金流入方。**方向**（支出 / 收入 / 转账）不是用户填的字段，而是由两条分录行的账户前缀确定性推导出来的结果：`to` 是 `Expenses:` 即支出，`from` 是 `Income:` 即收入，两端都是资金或负债账户即转账。这条不变量由 `TransactionInput` 的 `model_validator` 在**构造时**执行——`Income:` 落在 `to` 就自动换位，因此收入记反的值对象根本构造不出来，无论它来自 Agent、HTTP API 还是将来的导入脚本。`Expenses:` 落在 `from` 则**不换位**：那是退款的真实形态（支出账户记负数、资金账户记正数，账本里现存 1 笔），换位会把一笔退款写成一笔支出，符号整个反过来。因此只有收入这一侧是无歧义可归一的，支出侧的「反向」既可能是记反、也可能是退款，代码不替用户猜。

## Considered Options

**保留「资金账户 + 分类账户」这组角色，另加一个显式的 `direction` 字段**被否决。它更贴近用户说话的方式，追问文案和候选过滤也能直接由 `direction` 决定，不必回头看另一条分录行。但 `direction` 与账户前缀是两份可以互相矛盾的真相（`direction=income` 配上 `Expenses:` 的分类账户），校验代码等于把前缀规则再写一遍；而转账时「分类账户」这个角色根本不存在，必须开特例。相比之下，前缀推导只有一份真相，且三种方向共用同一套逻辑。

**只放宽 `prepare_ask` 的候选前缀，让 `Income:` 也能被选中**被否决。它让追问看起来能走通，却不改变 `render_transaction` 的符号规则——用户选完之后账依然记反。这是把 bug 藏起来而不是修掉。

**为转账新增第五个意图**被否决。转账在历史账本里有 47 笔（`Assets↔Assets` 31 笔、`Assets↔Liabilities` 14 笔、`Income↔Liabilities` 2 笔），比纯收入的 44 笔还多，确实值得支持；但它和支出、收入一样都是「新增一笔交易」，差别仅在方向，而方向是推导出来的派生概念，不该升格成意图。ADR 0001 还要求 Classify 的 prompt 保持静态以保住 prompt cache，为此改动 few-shot 不划算，何况「信用卡还款」「买基金」这类消息对 record 与 transfer 的边界本就模棱两可。

## Consequences

- 频次分布改为按 **from / to 角色**切分，而不是按「资金账户 / 分类账户」语义切分。归一化保证了角色位置稳定，因此同一套 `payee → from` / `payee → to` 在三种方向下都成立，转账不需要特例。`transaction_history()` 随之从只采集 Expenses 那条分录行，改为返回完整的三元组。
- **Extract 的 prompt 必须重写**。原文「from_account 是付款账户」正是收入记反的源头之一，新的说法是资金流出方 / 流入方，并列明三种方向各自的形态。
- **向量检索的价值上升**。索引里存的是 `render_entry()` 的成品 Beancount 原文（带真实符号），本就是资金流向的形态；召回的例子从此与字段语义一一对应，prompt 里可以直接说「照着相似历史的符号来」。若选了显式 `direction` 方案，例子与字段之间反而多一层翻译。
- **有些历史形态从此对话记不出来**，这是刻意接受的代价：
  - 把 `Income:` 当往来账户反向使用的写法（历史上 5 笔，全在 `Income:CN:Other`，如「替人垫饭钱」）。归一化会把它换位成标准收入方向。
  - 三条及以上分录行的交易（历史上 47 笔，如工资拆成应发 / 五险一金 / 实发）。`render_transaction` 只产出两条 posting，硬记会让差额凭空消失，因此 `extraction_issues()` 显式识别并拒绝，回复说明请在账本里手写，而不是静默吞掉。补齐它需要把 `TransactionInput` 从两个字段改成 postings 列表，是一次结构性手术。
  - `Equity:` 账户（历史上 12 笔 `Assets↔Equity`，期初余额与对账差额）。前缀规则不覆盖 Equity，因此它被排除在对话记账之外：不进候选集、不进自动补全、不进频次分布。手写与查询不受影响。
- 归一化是**静默换位**，不是报错。LLM 把两个账户选反属于常见且可自动纠正的错误，没有理由为此打断用户。
- 退款（`Expenses:` 在流出侧）推导出的方向是**转账**，因为它两端都不满足支出与收入的前缀条件。这个标签不够精确，但方向只有三个取值（CONTEXT.md），而退款既不是支出也不是收入；宁可落到最宽的那一格，也不为它开第四个取值。
