# 04 — 资金流向归一：收入与转账都记得出来

**What to build:** 用户说「今天发工资了，发了5000」，系统认得出这是收入，追问问的是「这笔钱进了哪个账户」并给出资产账户候选，确认后写进账本的是收入账户在负数侧、银行卡在正数侧的正确形态。用户说「支付宝转300到微信」或「还信用卡2000」，同样能记成转账并选到对手方。

这是本期主线，依据 ADR 0014。

把两条分录行的语义定死为资金流向：一条是资金流出方（记负数），一条是资金流入方。**方向**（支出 / 收入 / 转账）不是任何人填的字段，而是由两条分录行的账户前缀推导出来的结果——收入账户永远在流出侧，支出账户永远在流入侧，两端都是资金或负债账户即转账。

这条不变量落在**交易值对象的构造期**：收入账户落在流入侧时自动交换两条分录行，因此收入记反的交易根本构造不出来，绕过 Agent 的写入路径也一样。支出账户落在流出侧**不**换位——那是退款的真实形态，换位会把退款写成支出（ADR 0014 已记下这个例外）。归一是静默换位，不报错——LLM 把两个账户选反属于常见且可自动纠正的错误，没有理由为此打断用户。渲染逻辑不需要改，归一之后现有的符号规则本来就是正确的。

抽取的 prompt 必须一并重写。它现在写的是「from_account 是付款账户」，这句话本身就是收入记反的源头之一；改为资金流出方 / 流入方，并列明三种方向各自的形态。向量召回的相似历史是带真实符号的账本原文，与新语义一一对应，prompt 里可以直接指示照其符号填写。

追问的候选集改为由**已知的那条分录行**推导：已知流入侧是支出账户就给资金与负债账户；已知流出侧是收入账户就给资金账户；只知道一侧是资金账户就给支出、收入与其余资金账户。三个方向的分支一次写好——它们是一体的逻辑，拆开都不可单独验证。
