# 05 — 两个频次分布，两侧都自动补

**What to build:** 固定组合的消费一次都不用点。用户说「深圳通充值100」——历史上 53 次充值全是同一张卡、同一个分类——系统两侧账户都自动补上，直接给出待确认写入，不再追问。

账户置信度目前只从支出那条分录行上学，因此只有分类账户会被自动补，资金账户**从来不自动补**：只要用户没在消息里提到「微信」「支付宝」，就一定会弹一次追问。收入场景更糟——商户在支出历史里必然查不到，直接触发「新商户没有账户历史」。

改为维护两个频次分布：商户到流出账户、商户到流入账户，各自计算最高频占比、各自判阈值、各自决定是否自动补。按**分录行角色**切分而不是按「资金账户 / 分类账户」语义切分——04 的归一保证了角色位置稳定，因此同一套逻辑在三种方向下都成立，转账不需要特例。交易历史的采集随之从「只取支出那条分录行」改为返回商户与两侧账户的三元组，并在采集时排除权益账户。

ADR 0004 对置信度的定义（该商户历史中最高频账户所占的比例）不需要改，它本来就是按单个账户定义的。决策面板上的证据链要能同时展示两侧。

置信度阈值默认值同时从 0.70 定为 0.80。依据是在 1161 笔历史交易上的留一验证：0.80 是曲线拐点（流入侧准确率 80% → 85%，自动补率只从 32% 掉到 29%），再往上只掉覆盖不涨准确。

**注意**：本票会让自动补全的暴露面翻倍（两侧都会被猜）。08 的可编辑确认卡是它的安全网，两者要一起验证。

**Blocked by:** 04

**Status:** ready-for-agent

- [ ] 商户历史在两侧都高度一致时，两侧账户都被自动补上，不产生追问
- [ ] 某一侧历史一致、另一侧五五开时，只追问不确定的那一侧
- [ ] 用户在消息里明确说出的账户永远优先，不被历史猜测覆盖
- [ ] 收入与转账的历史同样进入分布，不再只学支出
- [ ] 权益账户不进入任何分布
- [ ] 新商户没有历史时两侧都转追问
- [ ] 决策面板的证据链能看到两侧各自的频次依据
- [ ] 置信度阈值默认值为 0.80，且可通过环境变量覆盖
