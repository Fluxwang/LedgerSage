# 03 — 拆开「抽取疑点」与「字段缺失」

**What to build:** 一次普通的追问不再白白多烧一轮 LLM。用户说「打车32」（没提用哪个账户），系统应当直接追问账户，而不是先把这条消息打回去重新分类一遍再问。

抽取节点目前把两类完全不同的东西塞进同一个列表：一类是「这条消息可能根本不是记账」的证据（含疑问词、日期是范围、缺明确金额主体、商户是品类词），另一类是「确实是记账，但差几个字段」。路由只看列表非空就打回重新分类，于是每一次正常追问都要多跑一轮分类加抽取——实测一条工资消息因此多花 8.3 秒，而重跑拿到的结果必然还是记账。

ADR 0001 对这条回边的设计意图写得很清楚：它只为「Extract 发现证据后打回 Classify」而存在。缺一个账户不是意图判断错了的证据。

拆成两个独立的东西：抽取疑点负责打回，字段缺失负责直接进追问。字段缺失要是**结构化**的（第几笔、缺流出侧还是流入侧），后面几张票的追问逻辑都要消费它。追问的问题文案随之由结构化信息生成，不再把内部诊断字符串拼进去——今天用户看到的是「第1笔请选择付款账户：缺少付款账户」这种自己重复自己的句子。

这是一张 prefactor 票：它本身可验证，同时让 04 的追问改造好写。

**Blocked by:** None — can start immediately

**Status:** ready-for-agent

- [ ] 仅因缺账户而追问时，一次运行的事件序列里只出现一次分类
- [ ] 抽取疑点（含疑问词 / 日期是范围 / 缺明确金额主体 / 商户是品类词）仍会打回重新分类，且仍最多打回一次
- [ ] 打回一次之后仍有疑点时转追问，不形成死循环
- [ ] 追问文案不再重复内部诊断信息，且能说明缺的是哪一笔的哪一侧
- [ ] 支出记账的既有行为不变
